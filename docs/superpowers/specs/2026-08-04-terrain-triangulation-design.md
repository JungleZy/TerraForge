## 结论先行

给地形切片管线加两项能力，**两者都默认开启，UI 上不给开关**（K 固定 0.15）：

1. **自适应三角化** —— 用自写的 Martini/RTIN 替代当前固定 65×65 规则网格，减面 **73.7%（山地）～82.7%（平缓）**。
2. **逐顶点法线** —— quantized-mesh 的 oct-encoded normals 扩展。必须配套 ghost cells，否则山地会出现可见的网格状接缝。

唯一给用户的开关是 **Cesium 的 `enableLighting`，默认关** —— 它是渲染端开关，切换不需重切片，法线数据先备着。

两项能力**互补而非互斥**：几何走 Martini 简化路径省三角形，法线走满网格路径保留光照细节（实测两者差异仅 1.3–1.6°，且 ghost cells 本就要求满网格采样，满网格法线是顺带产物）。

**排除了两条路，都是实测后排除的，不是没试过**：
- **QEM（PyMeshLab）** —— 质量确实更好（等质量下省 49% 三角形），但要 +281 MB 和 Qt/OpenGL 依赖，dist 从 378 MB 涨到 659 MB。
- **自研 TVD + Numba** —— 纯 Python 版质量能超过 QEM 8.5%，但 Numba 重写后优势缩到 1.5%，且有 9.21% 的忠实度偏差未定位；要 +193 MB 和 282 行自研代码。

## 背景：当前实现

`src/services/terrain_tiling/cesiumlab_terrain.py` 用的是**最朴素的规则网格三角化**：`_mesh_constants`（`:262-272`）双重循环，每个网格单元无条件切成两个三角形，拓扑只依赖网格尺寸 n，因此整张索引表可以 `lru_cache` 缓存。

生产参数 `tile_size=65`（`src/services/terrain_tiling/dem_task_tiler.py:22`），即每张瓦片恒定 **4225 顶点 / 8192 三角形**，与地形起伏完全无关。全仓 grep `delaunay|triangul|simplif|refine|collapse|quadric` **零命中**——不存在任何误差驱动逻辑。

这个方案的代价与红利都要说清楚，因为后续所有权衡都围绕它：

- **代价**：平坦区域浪费三角形（戈壁也是 8192 个），陡崖欠采样。
- **红利（容易被低估）**：相邻瓦片靠 `linspace` 端点共享同一经纬度、采同一份 DEM，**天然无缝，零成本**。自适应方案会失去它，必须显式解决。

## 插曲：验证时发现并修复了两个阻断性 bug（已落地，非待实施）

准备做渲染性能验证时发现**瓦片根本无法被 Cesium 解码**——也就是说在此之前，地形功能从未真正工作过。两个 bug 叠加，且全程静默：HTTP 全 200、任务标 completed、前端不报错。

**Bug 1（根因）**：`cesiumlab_terrain.py` 的 `IndexData.triangleCount` 写成了索引元素数。

```python
body.write(struct.pack("<I", len(encoded_indices)))       # 24576，错
body.write(struct.pack("<I", len(encoded_indices) // 3))  # 8192，对
```

spec 里该字段是**三角形数**，读端按 `triangleCount * 3` 取索引。写成元素数后 Cesium 去读 3 倍索引而越界，抛 `RangeError: Invalid typed array length: 73728`。紧邻的 `EdgeIndices` 用 `len(edge)` 是对的（spec 那里定义就是顶点数）。影响所有 `tile_size`（17 时是 1536 应为 512）。

**测试为什么没发现**：`tests/test_fix_terrain_mesh_indices.py` 的 `_parse` 用 `count=icount` 直接读索引——和编码端用了同一套错误约定，两边自洽所以一直通过。它的 docstring 写着「按 spec 逐字段解析」，但它解析的是实现。**测试镜像了实现的 bug**。已改为按 spec 的 `count=tri_count*3`，并新增 `test_triangle_count_field_holds_triangle_count_not_index_count` 直接钉住字段语义。

**Bug 2**：`static/js/map.js` 的 `CesiumTerrainProvider.fromUrl()` 传了 `${base}/layer.json`。该 API 收的是**目录 URL**，内部会 `appendForwardSlash()` 后再拼 `layer.json`，于是请求 `.../layer.json/layer.json` 得 404。更坑的是**它不 reject**：拿不到 layer.json 时静默按默认假设建 provider（实测 `hasWaterMask` 变成 `true`），随后瓦片请求全 404。已改为传 `base`。

验证：仅改 `triangleCount` 一个字段，同一批瓦片就从 `RangeError` 变为解码成功（8192 三角形 / 4225 顶点 / 四条边各 65 点 / minH 873.0 maxH 1163.8）；端到端加载后 34 个瓦片 `renderable: true`、`upsampled: false`。全量测试 969 passed。

**未验证的相关项**：`layer.json` 的 `parentUrl` 默认值是 `http://localhost:5000/terrain/base/layer.json`（以 layer.json 结尾）。它与 `fromUrl` 语义不同（Cesium 把它当 layer.json 文件 URL 做相对解析），当前值**很可能是对的**，但需要真实 base 地形数据才能实测。`docs/reference/terrain/README.md` 记录的「parentUrl 级联在 z0–4 不生效」现在需要在 bug 修复后重新复核——此前的观察可能只是这两个 bug 的表象。

### 统计方法（两个踩过的坑）

- **总量必须用均值加权，不能用中位数。** 总三角形数是求和，分布右偏（极陡瓦片拖尾），中位数会高估减面 1.5–2.4 个百分点。
- **跨方案比较必须配对。** 让每个方案的中位数在各自的有效子集上计算，会因为不同方案在不同瓦片上失败而导致中位数不可比——曾因此测出「QEM 锁定顶点比自由顶点质量更好」这种不可能的结果。正确做法：只保留所有方案都成功且三角形数逐个对齐的瓦片，每瓦片先算比值再取中位数。
- **质量评估基准统一到 257×257 真实采样点**（最接近真实地形），而非 65×65 自身。

## 一、Martini / RTIN 自适应三角化

### 算法与关键决定

RTIN（Evans et al. 1997，Mapbox Martini 是其现代实现）在 2^k+1 网格上预算各层误差，按阈值提取右三角二叉树。**65 = 2^6+1 天然匹配**当前 tile_size。

**决定 1：自写 numpy 实现，不用 pymartini。**

决定性理由不是维护状态未知，而是：**边界满密度必须在误差自底向上传播之前注入 `inf`**，黑盒库不提供这个钩子。第一版把 `inf` 设在 `compute_errors` 之后，边界约束完全失效，测出 93.4% 的假减面率；修正后是 84.8%。核心实现约 80 行。

**决定 2：跨瓦片无缝用「边界强制满密度」。**

RTIN 在瓦片内部保证无 T-junction（父三角形误差 = max(自身, 左子, 右子)），但这个保证**止于瓦片边界**——A 的东边界三角化由 A 内部误差决定，B 的西边界由 B 内部决定，必然不一致。

方案是把边界 4×64 = 256 个顶点的误差置 `inf`（在传播前），强制全部保留。**实测 2880/2880 = 100%**（东西向 + 南北向 × 三档位），相邻瓦片公共边顶点集合逐点一致，几何上不可能开缝。

额外红利：边界点全保留且顺序固定，quantized-mesh 需要的 west/south/east/north 边索引仍可预计算缓存。

**决定 3：误差计算按 RTIN 层级批量向量化。**

同层三角形彼此独立，12 个层级用 `np.maximum.at` 批处理。索引表只依赖 gridSize，可 `lru_cache`——与现有 `_mesh_constants` 完全同一模式。**实测加速 379x**（37.47ms → 0.099ms），与循环参考实现 **220/220 逐元素相同，最大绝对偏差 0**。

**决定 4：`max_error` 必须按层级缩放。**

固定绝对值不可用——`max_error=20m` 时 z14 瓦片只剩 2 个三角形（整块压成平面）。规则：`max_error(z) = K × 顶点间距(米)`，其中顶点间距 = `(180/2^z)/64 × 111320`。含义是允许的高程误差正比于水平分辨率，即**坡度误差容限恒定**。

### 实测：减面率（3518 样本，均值法按层瓦片数加权）

| 档位 | K | 山地 | 平缓 | z14 误差 |
|---|---|---|---|---|
| 精细 | 0.10 | 63.6% | 79.1% | 1.9 m |
| **标准** | **0.15** | **73.7%** | **82.7%** | 2.9 m |
| 激进 | 0.25 | 82.3% | 85.8% | 4.8 m |

### 实测：K 的响应曲线在 0.25 处饱和

| K | 0.02 | 0.05 | 0.08 | 0.10 | 0.15 | 0.25 | 0.50 | 1.00 |
|---|---|---|---|---|---|---|---|---|
| 减面 | 22.2% | 44.8% | 59.6% | 65.9% | 76.9% | **84.8%** | 88.4% | 88.8% |
| z14 误差 | 0.4m | 1.0m | 1.5m | 1.9m | 2.9m | 4.8m | 9.6m | 19.1m |

另有一个比饱和点更早生效的约束：**DEM 自身的垂直精度**。ASTER GDEM v3 约 ±17m(LE95)、Copernicus GLO-30 约 ±4m(LE90)（公开指标，未联网核实，按经验校准）。K=0.1 时误差 1.9m 远低于 DEM 噪声——那不是保留细节，是精确保留噪声。

### 实测：同屏三角形数 —— 几何不是 GPU 瓶颈

2026-08-04 补测。修复了下述两个阻断性 bug 后，用 Cesium 1.143 实际加载天山一个 granule（`tile_size=65`，12134 瓦片，z0–14），1280×800 画布、`maximumScreenSpaceError=2`：

| 视角 | 同屏瓦片 | 同屏三角形（不含裙边） | 同屏顶点 | 层级 |
|---|---|---|---|---|
| 2 km / 俯角 60° | 27 | 24,460 | 17,968 | z15×5, z16×22 |
| **8 km / 俯角 45°** | 34 | **278,528** | 152,490 | z12×13, z13×21 |
| 30 km / 俯角 70° | 19 | 155,648 | 85,215 | z11×19 |

三条结论：

1. **峰值同屏约 27.8 万三角形**，出现在中等视距（z12–13），与设计前的估算（20–40 万）吻合。这对现代 GPU 是很轻的负载——**几何不构成渲染瓶颈**。
2. 拉近到 2 km 时三角形数反而**降到 2.4 万**：视野落到 z15/z16，超出数据的 maxzoom=14，Cesium 改用父层 upsample，每片三角形远少于 8192。
3. 推论：**Martini 减面的价值主要在存储与传输（瓦片体积降 74–83%），不在渲染帧率**。同屏从 27.8 万降到约 7 万，对 GPU 都是无关紧要的量级。若动机是「拉近看卡」，瓶颈应先往影像图层或别处找。

测量环境注意：Playwright 在 WSL2 下是 SwiftShader **软件渲染**（无地形时就只有 5.1 fps），因此**帧率数据无参考价值**，上表只取与渲染器无关的几何量。

## 二、逐顶点法线与 ghost cells

### 接缝是真实存在的，且强烈依赖地形

顶点法线 = 邻接三角形面法线的面积加权和。**瓦片边界顶点只能拿到本瓦片内的三角形**，法线天生不完整 → 边界处光照突变。注意这个问题**即使不换三角化、只加法线也会出现**。

实测 1779 组相邻瓦片对（45° 斜射光下的 Lambert 亮度阶跃）：

| 数据集 | n | 接缝夹角 | 亮度阶跃 | >2% 阈值占比 |
|---|---|---|---|---|
| 山地 | 1757 | 4.23° | 3.25% | **81.9%** |
| 平缓 | 1761 | 0.91° | 0.79% | 22.7% |

按起伏分箱，分水岭在 **std ≈ 5–10m**：

| 起伏 | 接缝夹角 | 亮度阶跃 | >2% 占比 |
|---|---|---|---|
| 极平坦 <1m | 0.25° | 0.21% | **0.0%** |
| 平坦 1–3m | 0.49° | 0.38% | 4.1% |
| 微起伏 3–10m | 2.00° | 1.67% | 40.0% |
| 缓坡 10–30m | 3.14° | 2.60% | 66.7% |
| 中等 30–80m | 5.37° | 4.38% | 87.3% |
| 陡 80–200m | 5.77° | 4.53% | 93.9% |
| 极陡 >200m | 7.84° | 6.07% | **97.8%** |

准确表述是「**山地必然可见，平原基本无感**」。曾一度基于天山**内部**的平坦窗口（std<5m）得出「平坦地形也有 54.4% 超阈值」，那是错的——天山内部的平坦窗口周围仍是山地环境，不等于平原。真平原只有 22.7%。

补充判断依据：接缝**沿瓦片边界呈直线排列**。同样幅度下，结构化误差比随机噪声容易被看见得多，马赫带效应会把这条直线强化成可见网格。

### ghost cells：实测 100% 归零

采样从 65×65 扩到 67×67（`_worker_tile:383-384` 的 linspace 端点各外推一个步长），算完法线取中间 `[1:-1,1:-1]`。采样点增加 6.3%，是全部成本。

**实测 1080 组相邻瓦片，100% 精确归零**（最大残差 8.5e-07°，浮点噪声级），亮度阶跃 >2% 占比 **52.3% → 0.0%**。

不是「减小」而是数学上完全消除：加 ghost 后 A 东边界顶点与 B 西边界顶点的邻接三角形集合变得完全相同（同一地理位置采同一份 DEM），浮点运算逐位相同。

因为成本可忽略，**统一开启，不做成可选**。

### 两个已知坑

- **法线必须在 ECEF 空间算**，不是经纬度空间（经纬度下 1° 经距随纬度变化，直接算会让高纬地区法线系统性偏斜）。现成的 `lonlat_to_ecef` 可用。
- **ghost 环可能落在 DEM 范围外**。`DemSampler.sample`（`:219`）把越界/nodata 兜成 0，会在 DEM 边缘产生一圈朝向错误的假法线。需让边缘顶点法线退化为只用内侧三角形。

### 法线基于满网格算，不基于简化几何

三个理由，第二个是决定性的：

1. 精度略好（挽回 1.3–1.6° 法线偏差，约 1.5% 亮度）——单靠它不足以定夺。
2. **实现更简单**：满网格法线是规则的 numpy 切片累加（纯向量化）；简化几何要在不规则三角网上做 `np.add.at` 散射累加，更慢更绕。
3. ghost cells 本来就要求采样 67×67 满网格，满网格法线是顺带产物，零额外成本。

因此 Martini 与法线是**互补**的：几何走简化路径省三角形，法线走满网格路径保留光照细节，两个开关可独立打开而不互相拖累。

### 未验证项

法线接缝的严重程度**没有做真实渲染验证**——马赫带的实际可见度是感知问题，数值模型（Lambert 简化光照）只能近似。要更确定，需切两张相邻瓦片实际丢进 Cesium 开 `enableLighting` 目视。

前端目前 `static/js/map.js:1239` 的 `CesiumTerrainProvider.fromUrl()` 没传任何 options，`layer.json` 的 `extensions` 也是空数组——法线要生效，这两处都要改，且需开 `enableLighting`，否则法线不参与渲染。

## 三、排除的方案 A：QEM（PyMeshLab / fast-simplification / VTK）

### 质量优势是真的

等质量对比（162 瓦片，把 Martini 二分调参到与 QEM 相同 RMS）：

| | 三角形数 | RMS |
|---|---|---|
| Martini K=0.15 | 1314 | 1.20 m |
| QEM 同三角形数 | 1314 | **0.53 m** |
| Martini 达到 0.53m 所需 | **2666** | 0.53 m |

**Martini 需要 1.96x 三角形才能追平 QEM**（IQR [1.82, 2.09]），优势在所有分组稳定：山地 1.88x、平缓 2.05x、极陡 1.51x。

### 优势来源分解（关掉 optimalplacement 做受控对比）

| 方案 | RMS | 顶点在原格点比例 |
|---|---|---|
| Martini（RTIN 拓扑 + 格点约束） | 1.678 m | 100% |
| QEM `optimalplacement=False`（自由拓扑 + 格点约束） | 1.051 m | 100% |
| QEM `optimalplacement=True` | 0.909 m | 32.7% |

- **拓扑自由占总优势的 81.5%**
- 顶点位置自由占 18.5%

即 QEM 赢主要不是因为顶点能自由移动，而是能任意选择坍缩哪条边。RTIN 的固定二叉细分模式正是它换取「无 T-junction + 边界确定性」的代价——**想拿回这 81.5% 就得放弃 RTIN 结构**。

### 库横评：体积与边界保持不可兼得

| | 边界保持 | 体积 | dist 影响（当前 378 MB） | 耗时/瓦片 |
|---|---|---|---|---|
| **PyMeshLab** | **256/256** (`preserveboundary=True`) | +281 MB | → 659 MB (+74%) | 33.5 ms |
| fast-simplification | **20/256** ✗ | +5.7 MB | +1.5% | 4.6 ms |
| vedo / pyvista | VTK 有参数，未深测 | +638 MB | → 1 GB (+169%) | — |

fast-simplification 体积理想但**锁不了边界**——Python 层完全没暴露 border/mask/lock 参数（底层是 C 扩展），要改就得动 C++ 源码重新编译。reduction=0.8 时 256 个边界顶点只精确保留 20 个，0.9 时只剩 3 个，相邻瓦片会产生真正的**几何裂缝**（比法线接缝严重得多）。

### 排除理由

不是算法不行——算法行。是**质量优势换不来体积代价**：

1. dist 从 378 MB 涨到 659 MB（+74%），只为省一半三角形。
2. **Qt + OpenGL 是真实风险，不是理论风险**。在本轮的 headless Linux 上就实际踩到：`libfilter_meshing.so` 因缺 `libOpenGL.so.0` 直接加载失败，QEM filter 根本不可用，是做了 `libGL.so.1` 的软链接 shim 才跑起来。Windows/macOS 桌面自带 OpenGL 没问题，Linux 部署会遇到同样的坑（需 `libglvnd0`）。
3. **边际收益递减**。Martini 标准档已减面 73.7–82.7%，QEM 到 87–91%。而实测同屏峰值只有 27.8 万三角形（见第一章末），减到 7 万还是 3.5 万，对现代 GPU 都是无关紧要的量级。

## 四、排除的方案 B：自研 TVD + Numba

### 动机与设计

QEM 是通用 3D 网格算法，**没有利用地形是 2.5D 高度场**这个结构。TVD（Terrain Vertical-error Decimation）针对这点：

1. **代价 = 真实垂直高程误差增量**。QEM 最小化 3D 点到平面距离，而评估标准是垂直误差——陡坡上两者差 cos(坡度)，QEM 系统性低估陡坡误差。
2. **半边坍缩**（坍缩到端点而非新位置），顶点始终留在原格点，边界可硬锁。
3. **收尾全局 z 最小二乘精修**（边界固定，共轭梯度），QEM 坍缩后位置即固定，无此步。

合法性靠 link condition + 翻转检测强制保证（第一版漏了这两个检查，产出覆盖率 0% 的非法三角网）。

### 实测：纯 Python 版确实超过 QEM

配对比较（13 个所有方案都成功、三角形数逐个对齐的瓦片）：

| 方案 | RMS | 配对比值 vs QEM | 胜率 |
|---|---|---|---|
| Martini K=0.15 | 1.115 m | 1.746x | 0% |
| QEM（顶点锁格点） | 0.605 m | 1.174x | 0% |
| QEM optimalplacement | 0.516 m | 1.000x | — |
| TVD | 0.490 m | 0.957x | 76.9% |
| **TVD + z 精修** | **0.471 m** | **0.915x** | **92.3%** |

**受控对比更干净**：QEM 顶点也锁格点时（与 TVD 同约束），TVD/QEM = **0.823x，100% 胜率**。这验证了核心假设——垂直误差度量确实更适合地形。

但**纯 Python 12.7 s/瓦片**，是 QEM 的 400 倍，全量要 57 小时。且优化尝试失败：把代价函数从「完整邻域重定位」降到「只算一个点」，工作量减少一个数量级，**加速比 1.0x**——瓶颈是 Python 的 `set`/`dict`/`heapq` 对象开销，不是计算量。

### 实测：Numba 三个前提全部通过

| 前提 | 结果 |
|---|---|
| 加速 | **438x**，12.7 s → 91.8 ms |
| **Nuitka 打包 Numba** | **完全可行**——编译通过、产物能跑、JIT 正常，无需插件 |
| JIT 冷启动 | `cache=True` 有效，11.84 s → 0.35 s；打包后需 `NUMBA_CACHE_DIR` 指向可写目录 |
| 体积 | +193 MB（llvmlite 独占 172 MB），dist 378 → 571 MB (+51%) |

### 但质量优势在重写中蒸发

| 版本 | vs QEM | 胜率 |
|---|---|---|
| TVD 纯 Python | 0.915x（好 8.5%） | 92.3% |
| **TVD-numba** | **0.985x（好 1.5%）** | 61.1% |

平均忠实度偏差 **9.21%**，根因未定位。改 tie-breaking 试图对齐反而更差（4.03% → 9.21%）——因为**Python 版自己就不是确定性算法**：主循环 `for w in nb|{u}` 遍历 set，迭代顺序取决于哈希，同样输入不保证同样的坍缩序列。「忠实复现」这个目标本身不成立。

另外 **cheap 模式完全失败**（第二次踩同一个坑）：工作量砍掉一个数量级，耗时 89.4 ms vs 91.8 ms 几乎不变，质量从 1.037x 跌到 1.558x。

重写过程还暴露一个静默 bug：`MAXD=64` 容量溢出——坍缩使顶点度数增长，超容量后新三角形静默加不进邻接表，`_legal` 基于残缺信息判定合法，输出重叠三角形。已修为 256 + `_cost` 容量检查 + 输出自检。

### 排除理由

| | Martini | QEM | TVD-numba |
|---|---|---|---|
| 质量 vs QEM | 1.85x 差 | 1.00x | 0.985x（好 1.5%） |
| 耗时/瓦片 | **5.6 ms** | 33.5 ms | 98 ms |
| 全量 66213 瓦片 / 4 workers | **1.6 分钟** | 9.2 分钟 | 27.1 分钟 |
| 依赖体积 | **0** | +281 MB | +193 MB |
| 自研代码量 | 80 行 | 0 | **282 行**（已暴露 2 个坑） |

拿 1.5% 质量优势，付出速度慢 2.9x、282 行有微妙 bug 风险的自研代码、一个未定位的忠实度问题，只换回 88 MB。**交易不成立。**

TVD 的价值是**证明了上限在哪**：若将来项目愿意维护编译扩展（Cython/Rust），垂直误差度量 + z 精修是质量最优方向。现在不值得。

### 顶点重排与编码向量化，绑定在自适应上做

实测：规则网格下做顶点重排会让索引段 gzip **从 233 B 涨到 613 B**——当前无重排的编码值虽大（50% 是 uint32 下溢产生的 4294967233 这类大数），但序列极度规律，gzip 的 LZ77 压得极狠。

Martini 索引本身无周期性，这份「规律性红利」自动消失，届时重排的压缩劣势基本抵消，而它换来的向量化编码是刚需（拓扑逐瓦片变化，`lru_cache` 失效，`_high_water_mark_encode` 的纯 Python 逐元素循环会变成每瓦片对约 24576 个元素跑一遍）。

已验证的向量化写法（依赖重排）：

```python
_, first_pos = np.unique(indices, return_index=True)
is_first = np.zeros(len(indices), bool); is_first[np.sort(first_pos)] = True
highest = np.cumsum(is_first) - is_first     # 等价于循环里的 highest
encoded = (highest - reordered).astype(np.uint32)
```

**所以：编码改造不是独立议题，与 Martini 绑在一起做或都不做。**

### 参数决策：不给用户选，K 固定 0.15

**Martini 与法线都默认开启，UI 上没有任何开关。** 原先设计的「切片精度三档 + 高级 K」取消——多一个用户看不懂的旋钮不如给一个验证过的默认值。

`max_error` 系数固定 **K = 0.15**：

| 档位（仅作选值依据，不进 UI） | K | 减面（山地/平缓） | z14 误差 |
|---|---|---|---|
| 精细 | 0.10 | 63.6% / 79.1% | 1.9 m |
| **采用** | **0.15** | **73.7% / 82.7%** | **2.9 m** |
| 激进 | 0.25 | 82.3% / 85.8% | 4.8 m |

选 0.15 的依据：K > 0.25 收益饱和（边界满密度构成 11.2% 的地板，再调只增误差不减三角形）；K < 0.10 时误差 1.9m 已低于 DEM 自身垂直精度（ASTER ±17m、GLO-30 ±4m），那是在精确保留噪声。0.15 是曲线上兼顾两端的点。

### 地形光照：渲染端开关，默认关

法线数据**无条件写入**，但 Cesium 的 `globe.enableLighting` 做成 **UI 开关且默认关**。

理由：`enableLighting` 是纯渲染端开关，**切换不需要重切片**。默认开会改变所有现有预览的外观——卫星影像本身已含光照信息，再叠一层可能显得过暗或有双重阴影；`lyrs=m` 路网图是矢量风格，加光照更不协调。默认关则法线数据先备着（每顶点 2 字节，成本可忽略），用户想看地形起伏时随手打开，即时生效。

代价是不开灯时那 2 字节确实白存。接受——它换来的是「随时能开」而不必重切 12000 个瓦片。

## 附录 A：TVD 原型的核心逻辑

完整原型约 180 行（纯 Python）/ 282 行（Numba 全数组版），**是质量上限的探针，不是生产代码，未入库**——它有已知缺陷（Numba 版与 Python 版存在 9.21% 未定位的行为偏差，且 Python 版因 set 迭代顺序而非确定性），入库反而会误导后人以为可直接用。下面记录的是算法精髓，据此可重新实现。核心部分：

```python

def _cost(self, v1, v2):
    if not self._legal(v1, v2):          # link condition + 翻转检测，缺一不可
        return np.inf, None
    ts, qi = self._ring(v1)              # v1 的 1-ring 三角形 + 落在其中的原始格点
    newt = [np.where(tri == v1, v2, tri) for t in ts if v2 not in self.T[t]]
    best, who = self._locate(newt, qi)   # 在新三角形里定位并插值
    if np.isnan(best).any():
        return np.inf, None              # 有点掉出新网格 -> 拒绝
    ne = np.abs(best - self.P[qi, 2])
    return float((ne**2).sum() - (self.err[qi]**2).sum()), (...)

def _legal(self, v1, v2):
    # link condition：N(v1) ∩ N(v2) 必须恰好等于共享边的对端顶点集
    shared = [t for t in (self.v2t[v1] & self.v2t[v2]) if self.alive_t[t]]
    opp = {u for t in shared for u in self.T[t] if u not in (v1, v2)}
    if (self._nbrs(v1) & self._nbrs(v2)) != opp:
        return False
    # 翻转检测：坍缩后每个三角形的有向面积不能变号
    for t in self.v2t[v1]:
        tri = self.T[t]
        if v2 in tri: continue
        new = np.where(tri == v1, v2, tri)
        if _sarea(self.P[new][:, :2]) * _sarea(self.P[tri][:, :2]) <= 0:
            return False
    return True
```

z 精修（固定拓扑与边界，共轭梯度解最小二乘，免 scipy）：对每个原始格点在当前三角网上求重心坐标得到插值矩阵 `A`，边界顶点 z 作为已知项移到右端，解 `min ‖A z − b‖²`。实测对 Martini 拓扑值 21.5%，对 TVD 拓扑值约 4%，**边界 z 逐点不变**（162/162 验证）。

## 附录 B：本轮踩过的坑

按「会不会再犯」排序，前四条都产生过假数字：

1. **边界 `inf` 注入时机**。设在误差传播之后，边界约束完全失效，测出 93.4% 的假减面率（真值 84.8%）。RTIN 误差自底向上传播，`inf` 必须在传播**之前**注入才能到达祖先三角形。
2. **总量统计用中位数**。三角形总数是求和，必须用均值加权；中位数高估减面 1.5–2.4 pp。
3. **跨方案比较不配对**。各方案中位数在各自有效子集上算，导致「QEM 锁定顶点比自由顶点更好」这种不可能的结论。必须只保留全部方案都成功且三角形数对齐的瓦片。
4. **以偏概全的地形样本**。只用天山（全山地）得出的法线接缝结论（「平坦地形也有 54.4% 超阈值」）被真平原数据推翻（22.7%）。天山内部的平坦窗口 ≠ 平原。
5. **边坍缩漏合法性检查**。link condition + 翻转检测缺一，产出覆盖率 0% 的非法三角网。
6. **固定容量邻接表静默溢出**。`MAXD=64` 在坍缩中被突破后，新三角形静默丢弃，邻接表残缺，`_legal` 据此误判。必须在 `_cost` 里加容量检查 + 输出自检。
7. **两次误判性能瓶颈**。先后假设瓶颈在「代价函数的点数」，两次把工作量砍掉一个数量级，两次加速比都是 1.0x。真瓶颈第一次是 Python 对象开销，第二次在 Numba 版里仍未定位。**优化前先测，别猜。**
8. **环境相关**：`/tmp` 有激进清理机制，实验数据与 venv 全部丢失过一次，应放 `~/.cache`；PyMeshLab 在 headless Linux 需 `libOpenGL.so.0`（libglvnd）；后台运行必须显式带 `LD_LIBRARY_PATH`/`QT_QPA_PLATFORM`，漏掉会让 QEM 静默返回 nan（犯过两次）。
