## 读之前必须知道的两条

1. **报告里的「已修复 / 已处理完毕 / 已上线」只对撰写当天有效。** 那是作者在那一天核实的结论，不是持续维护的状态位。代码此后一直在动，同一处可能被改回去、被重构掉、或被新问题覆盖。任何一条要当依据用，都得回代码验一遍。
2. **正文不回改。** 报告里的 `file:line`、测试通过数、版本号、目录路径全是当日快照。改掉等于伪造审查记录，所以一律保持原样——文件内部指向已移动位置的路径是有意保留的历史原貌，不是待修死链。

## ⚠️ 2026-07-31 那份的「全部处理完毕」不能全信

`2026-07-31-code-only-review.md:11` 写着「全部 HIGH、MEDIUM、LOW 项及已知遗留①-④均已处理完毕」。**其中 MEDIUM #21 当时没有收敛**：测试隔离虽然新增了 `conftest` 的 `fresh_import` 工具，但各测试文件里手写的 `sys.modules.pop` 清单并没有整批迁过去。三天后 `2026-08-03-full-project-review.md` 的 **M23** 以「〔上轮已提出仍未修〕」重新提出了同一条。

**这一条现在从「数文件」改成了棘轮，判据在 `tests/test_conftest_isolation_contract.py`。** 它不要求把所有手写 pop 都迁走——上一轮试过在 conftest 里全局施加恢复语义，直接打红 15 条——而是钉住真正会出事的那个组合：某个模块被裸 `pop`（不恢复）的同时又被别的文件在**模块级** `from` 导入，于是同一个类存在两份对象，`pytest.raises` / `except` / `isinstance` 随文件执行顺序时绿时红。名单 `KNOWN_DOUBLE_INSTANCE_RISKS` 已清空，两侧都有断言：新增这种组合会红，名单里留着已修条目也会红。

所以这里不再写「`tests/` 下还有多少个文件手写清单」。那个数字每周都在变（本 README 曾写 48，同日实数 56），而且它从来不是判据——判据是上面那个文件跑不跑得过。
