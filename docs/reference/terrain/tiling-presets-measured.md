# 高程切片三档预设：实测选型

> **测量时间**：2026-08-08 | 6 个真实 Copernicus GLO-30 granule（1°×1°，坡度中位 0.51~38.85，覆盖极平原到黄土塬）、**20 个配置 × 6 地形 = 102 组完整金字塔扫描**、多轮专项复测，外加**真实 CesiumJS 1.143.0 + WebGL 的客户端渲染实测**。精度全部从**落盘瓦片解码后**对源栅格量得。
> 本文只做测量与选型，**没有改动任何生产代码**。测量台在 `~/.cache/mapdl-probe/preset_eval/`。

---

## 一、结论先行

**三档定义**（`tile_size` 恒为 65 不动，`max_error_k` 在 grid 后端下不参与计算）：

| 档位 | `triangulator` | `max_level` | `normals` | 顶点间距 |
|---|---|---|---|---|
| **精度** | `grid` | `est + 1` | 跟随光照开关 | ≈ 0.3× 源像素 |
| **均衡**（默认） | `grid` | `est` | **关** | ≈ 0.6× 源像素 |
| **速度** | `grid` | `est − 1` | **关** | ≈ 1.2× 源像素 |

`est` = `GeographicTilingScheme(tile_size=65).estimate_max_level(源像素度数)`，**按源 DEM 分辨率现算**，不是固定值。

四条支撑结论，每条都在下面有数据：

1. **三档都用 `grid`，一个都不用现行的 `auto`。** 现行默认在 6 个 DEM 上**一个 Pareto 前沿都没进**，被三轴全面支配。
2. **档位靠 `max_level` 拉开，不靠简化后端。** 两者都能换体积，但兑换率差 2.4~3.9 倍，且层级旋钮**省时间**、后端旋钮**多花 2.6~5.9 倍时间**。
3. **法线应该从档位里拆出来做独立开关，默认关。** 它对几何精度零贡献，却吃 +35%~+100% 字节和约 2.1 倍时间，而前端光照本来就默认关。
4. **`grid` 的三角形数暴涨不影响客户端渲染。** 真实 Cesium 实测：同屏瓦片数逐格相同、三角形多 4~5 倍而**帧时在噪声内**（32 万三角形、0.3~0.4 ms/帧、显存 6 MB）。唯一代价是首次加载按字节等比变长（平缓地形 1.74 倍，崎岖地形无差别）。见第八节。

## 三、为什么现行默认必须换掉

### 3.1 它不在 Pareto 前沿上 —— 6 个 DEM，0 次

对全部 20 个候选配置做三轴（墙钟 / 字节 / RMS，全部越小越好）严格支配判定。**「进入前沿次数」= 在多少个 DEM 上没有被任何其他配置三轴全面支配**：

| 配置 | 进入前沿次数 | 备注 |
|---|---|---|
| `grid` @est−2 法线关 | **6 / 6** | |
| `auto` @est−2 法线关 | **6 / 6** | 字节最省的极端档 |
| **`grid` @est−1 法线关** | **6 / 6** | ← **速度档** |
| **`grid` @est 法线关** | **6 / 6** | ← **均衡档** |
| **`grid` @est+1 法线关** | **3 / 3** | ← **精度档** |
| `grid` @est−1 法线开 | 2 / 6 | |
| `auto` @est−1 法线关 | 2 / 6 | |
| `auto` @est 法线关 | 1 / 6 | |
| `auto` @est−1 法线开 | 1 / 6 | |
| `tile_size=129` + `grid` | 1 / 3 | |
| **`auto` K=0.15 @est 法线开（现行默认）** | **0 / 6** | |
| `martini` K=0.15 @est | 0 / 6 | |
| `auto` K=0.30 @est / `auto` K=0.60 @est | 0 / 6 | |
| `grid` @est 法线开 / @est−2 法线开 / @est+1 法线开 | 0 / 6、0 / 6、0 / 3 | |
| `auto` K=0.05 @est | 0 / 3 | |
| `tile_size=129` + `auto` / `tile_size=33` + `auto` | 0 / 3 | |

**选中的三档全部落在前沿上。** 反过来看两条规律：**所有开法线的配置都掉出前沿**（法线是功能开关，不在这三个轴上换取任何东西），**所有简化后端的配置除了 `@est−2` 那个字节极端档之外也全部掉出前沿**。

现行默认被谁支配（全配置集下逐 DEM 复核）：**6/6 个 DEM 上被「同配置但关法线」支配**，**5/6 上被 `grid @est−1` 支配**，最崎岖的 loess 上被 `grid @est 法线关` 支配。

### 3.2 简化后端在崎岖地形上是负收益

gzip 之后规则网格约 **1.026 字节/三角形**、Martini 约 **4.081 字节/三角形**（每个三角形贵 4 倍），**减面必须超过 74.9% 才在字节上打平**（无法线口径，数据见 [`triangulation-backends-measured.md`](triangulation-backends-measured.md)）。崎岖地形减不到这个幅度。

loess @est 实测（法线统一关，只比几何）：

| 后端 | 体积 | RMS |
|---|---|---|
| `grid` | 94.5 MB | 0.534 m |
| `martini` | **143.9 MB** | 1.082 m |

**martini 比 grid 大 52%，精度还差 2.0 倍。** `auto` 逐瓦片择优能识别出这一点（loess 上它 **98.8%** 的瓦片选了 grid，产物与纯 grid 几乎一致），但代价是**两个后端各编一遍各压一遍** —— 白花的 CPU 换来一个和 grid 差不多的产物。

### 3.3 时间花在哪：`rtin_extract` 占 58%

单瓦片成本分解（loess z14，`tile_size=65`，`auto` + 法线，进程内 best-of-N）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| `rtin_extract` 自适应三角化 | 4.43 ms | **57.7%** |
| 法线（采样 + 叉积） | 0.79 ms | 10.2% |
| gzip(martini) | 0.78 ms | 10.2% |
| encode(martini) | 0.66 ms | 8.6% |
| encode(grid) | 0.38 ms | 4.9% |
| gzip(grid) | 0.35 ms | 4.5% |
| **DEM 采样** | **0.19 ms** | **2.5%** |
| `rtin_errors` | 0.10 ms | 1.3% |

两个反直觉点：

- **GDAL 采样只占 2.5%**，不是瓶颈。切片是 CPU-bound 在纯 Python 的三角化上。
- `rtin_extract`（`rtin.py:106-159`）是纯 Python 递归，每个三角形 3 次 dict 查找，成本正比于**产出三角形数** —— 所以它在崎岖地形上更贵（loess 2606 三角形 → 4.43 ms）、平缓地形上便宜（huabei 930 三角形 → 1.02 ms）。这解释了为什么 `auto` 相对 `grid` 的减速是 2.6×~5.9× 随地形浮动。

改用 `grid` 直接绕开整条 rtin 路径 + 第二次编码 + 第二次压缩：**单瓦片 7.68 ms → 1.71 ms，快 4.5 倍**。

## 四、为什么档位靠 `max_level` 而不是靠简化后端

两个旋钮都能拿精度换体积。从「`grid` @est、法线关」这个共同基线出发各走一步：

**性价比 = 体积压缩倍数 ÷ RMS 劣化倍数**，>1 表示这笔交易划算。

| 地形 | 旋钮 | 尺子甲<br>（连续双线性曲面） | 尺子乙<br>（源像素中心实测值） | 时间 |
|---|---|---|---|---|
| huabei | **降一级** | 3.85÷2.63 = **1.46** | 3.85÷1.85 = **2.09** | **省 2.52×** |
| | 换 `auto` | 2.49÷6.77 = **0.37** | 2.49÷3.33 = **0.75** | 多花 2.58× |
| jiangnan | **降一级** | 3.82÷2.69 = **1.42** | 3.82÷1.90 = **2.00** | **省 2.48×** |
| | 换 `auto` | 1.51÷2.77 = **0.55** | 1.51÷1.79 = **0.85** | 多花 3.38× |
| loess | **降一级** | 3.79÷2.84 = **1.34** | 3.79÷1.94 = **1.95** | **省 2.65×** |
| | 换 `auto` | 1.00÷1.00 = 1.00 | 1.00÷1.00 = 1.00 | 多花 5.94× |

（loess 那两行是 1.00：法线关掉后 `auto` 98.8% 选 grid，两者本就是同一个产物 —— 但仍然多花了 5.94 倍时间。）

两把尺子给出同一个方向：**层级旋钮的效率是简化后端的 2.4~3.9 倍，而且它省时间、后端花时间。**

### 层级的兑换率高度稳定，与源分辨率无关

把 loess 重采样成 3″（93 m）和 9″（278 m），各自建 5 个层级：

| 源分辨率 | 每加一级的体积倍数 | 每加一级的精度倍数 |
|---|---|---|
| 1″ (31 m) | ×3.8 / ×3.6 / ×3.05 | ÷2.84 / ÷2.74 / ÷2.91 |
| 3″ (93 m) | ×3.6 / ×3.1 | ÷2.77 / ÷2.80 |
| 9″ (278 m) | ×2.7 / ×2.8 | ÷3.05 / ÷2.92 |

**加一级 ≈ 3.3 倍体积换 2.8 倍精度**，六组数据全部落在这个区间。这就是三档能等距拉开、且行为可预测的依据。

### `est` 是约定，不是精度悬崖 —— 我原来的两个假设都错了

我先后假设过「超出源分辨率的层级是纯浪费」，用两把尺子各验一次，**两次都被数据否掉**：

| loess | 尺子甲（连续双线性曲面） | 尺子乙（源像素中心实测值） |
|---|---|---|
| z13 | 1.5146 m | 2.4467 m |
| z14（= est） | 0.5342 m | 1.2602 m |
| z15 | 0.1947 m | **0.6331 m** |

越过 `est` 之后**两把尺子都在继续降**，没有平台期。原因：`est` 层顶点间距（19.1 m）虽已细于源像素（31 m），但顶点不落在像素中心上，取值是「双线性采样 → 再线性插值」的二次残差，只随网格加密平滑收敛，不存在阈值。

**所以 `estimate_max_level` 是一个约定（间距 ≈ 源像素），不是物理门槛。** 拿它当「均衡」的锚点，是因为它可解释、可按源自适应，不是因为越过它就没用了。

## 五、法线：拆成独立开关，默认关

法线（`octvertexnormals`）**对几何精度零贡献** —— 开关两侧 RMS / P95 / 最大误差逐位相同。它的代价：

| DEM | 关 | 开 | 字节代价 | 时间代价 |
|---|---|---|---|---|
| huabei | 94.6 MB / 3.90 s | 127.2 MB / 8.18 s | **+35%** | **2.10×** |
| jiangnan | 91.9 MB / 3.87 s | 153.3 MB / 8.03 s | **+67%** | **2.08×** |
| loess | 94.5 MB / 3.84 s | 189.3 MB / 8.16 s | **+100%** | **2.13×** |

而前端 `enableLighting` **默认是关的**（`static/js/terrain_lighting.js:46-52`），偏好只存 localStorage 键 `tf-terrain-lighting`（`:34`、`:72`），不进配置表。

### 一条非显然的连锁反应：法线会把 `auto` 推向更差的后端

法线是每顶点 2 字节，`grid` 顶点最多（4225）、被罚得最狠，于是逐瓦片择优被系统性地推向 martini：

| loess | 选 martini | 选 grid | martini 占比 | RMS |
|---|---|---|---|---|
| `auto` 法线**开** | 8098 | 3973 | **67.1%** | 1.040 m |
| `auto` 法线**关** | 146 | 11925 | **1.2%** | **0.520 m** |

**关掉法线不只省时间省体积，还顺带让择优选对后端，精度直接翻倍。** 换成 `grid` 之后这条自动消失（不再有择优），但它解释了现行默认为什么精度那么差。

### 风险：关法线是**静默**降级

`normals=False` 会让 `layer.json` 的 `extensions` 写成 `[]`（`cesiumlab_terrain.py:1548`）。Cesium 的 `hasVertexNormals` 是 **provider 级单一标志**，于是：

- 光照按钮点了没有地形明暗，退化成全球日夜渐变，**全程零报错**；
- 植入的随包 base 自带法线也一起作废（`merge_base_availability` 不修改 `extensions`，`layer_json.py:137-142`）。

**这个项目栽过三次「作业 completed、HTTP 200、前端不报错、就是不对」的跟头。** 所以法线该做成独立勾选项并在 UI 上写明「关闭后地形光照不可用」，而不是藏在档位里静默生效。切完再想开只能重切 —— 法线是烘焙进瓦片的。

## 六、顺带查出的现存缺陷：`maxzoom` 不看源分辨率

应用侧**恒传** `maxzoom`（配置键 `terrain_local_maxzoom` 默认 14，`database.py:91`；`dem_task_manager.py:308-330`），`build_terrain` 里的 `estimate_max_level` 因此从不生效。后果双向：

- **源比 30 m 粗时超建。** 3″（93 m）DEM 建到 z14 = 77.4 MB / 12071 张；按 `est`(=12) 建 = 6.9 MB / 1445 张。**11 倍体积**换来的只是对同一批 93 m 数据更平滑的插值，不含任何新地形。
- **源比 30 m 细时欠建。** 5 m DEM 的 `est` 约 17，被固定的 14 截断，源数据的细节根本没进瓦片。

三档按 `est` 现算，等于顺手修掉这条。对最常见的 1″ Copernicus GLO-30，`est` 正好 = 14，**层级与今天一致**，不会让现有用户的产物层级发生意外变化。

## 七、均衡档相对现状的账，把话说全

| DEM | 坡度中位 | 现状 | 均衡 | 体积变化 | 精度提升 |
|---|---|---|---|---|---|
| netherlands | 0.51 | 12.9 MB / 1.086 m | 18.9 MB / 0.331 m | **+46%** | 3.3× |
| huabei | 0.66 | 44.5 MB / 0.543 m | 94.6 MB / 0.082 m | **+112%** | 6.6× |
| jianghan | 1.18 | 53.5 MB / 0.729 m | 90.7 MB / 0.132 m | **+70%** | 5.5× |
| tarim | 2.21 | 53.7 MB / 0.853 m | 95.1 MB / 0.159 m | **+77%** | 5.4× |
| jiangnan | 5.06 | 85.8 MB / 0.891 m | 91.9 MB / 0.185 m | **+7%** | 4.8× |

**中位数：体积 +58%，精度 5.1×，时间约 1/5。**

体积是唯一变差的轴，而且只在平缓地形上变差（崎岖地形反而省 45%）。**在意磁盘的用户选「速度」档就行** —— 它 24.6 MB，比现状的 44.5 MB 还小，精度还好 2.4 倍。

如果不接受默认档涨体积，替代锚点是「均衡 = `grid` @est−1」：体积全面小于现状、精度 5/6 优于现状，但最崎岖地形上精度会从 1.040 退到 1.449。

**我推荐锚在 `est`。** 理由：默认档不应该在任何轴上让视觉质量比今天差，而磁盘是三个轴里最容易补救的一个（用户改档即可，不必重装、不必改配置）。

## 八、客户端影响实测：grid 让每张瓦片恒定 8192 个三角形，Cesium 吃得消吗？

这是本方案最该被质疑的地方：`grid` 不做减面，**平缓地形上每张瓦片的三角形数会涨到 auto 的 7.86 倍**（huabei 实测每瓦片 8192 vs 1042，顶点 4225 vs 650）。崎岖地形上则毫无差别（loess 1.01 倍，因为 auto 本来就选 grid）。

**实测结论：渲染侧零影响，只有加载耗时按字节等比变长。**

环境：本仓 vendored CesiumJS 1.143.0、真实 WebGL（ANGLE / Intel UHD 620 核显 —— 刻意用弱 GPU）、1600×900、无影像图层、关大气/雾/光照，手动泵 `scene.render()` 计时（隐藏标签页里 rAF 与 setTimeout 都被节流，见第十一节的两个坑）。

| 场景 | 数据集 | 同屏瓦片 | 同屏三角形 | 显存 | 帧时中位 | P95 |
|---|---|---|---|---|---|---|
| huabei sse=2（Cesium 默认） | auto | 23 | 37,114 | 0.78 MB | 0.5 ms | 1.0 ms |
| | **grid** | **23** | **155,392**（4.2×） | 3.03 MB | **0.3 ms** | 0.5 ms |
| huabei sse=1（2 倍质量） | auto | 45 | 64,153 | 1.28 MB | 0.6 ms | 1.2 ms |
| | **grid** | **45** | **319,576**（5.0×） | 5.82 MB | **0.4 ms** | 0.5 ms |
| loess sse=1（对照） | auto | 48 | 289,707 | 5.21 MB | 0.6 ms | — |
| | **grid** | **48** | 338,753（1.17×） | 6.15 MB | 0.7 ms | — |

三条：

1. **同屏瓦片数逐格相同**（23/23、45/45、48/48，层级分布也一致）。Cesium 的 LOD 选择由 `layer.json` 的几何误差与 `maximumScreenSpaceError` 驱动，**与瓦片内三角形数无关** —— grid 不会让客户端多请求一张瓦片。
2. **帧时在噪声内，grid 甚至略快**（0.3 vs 0.5 ms）。32 万同屏三角形对任何 GPU 都是小数目；这个量级下瓶颈是逐瓦片的 draw call 与剔除开销，而那部分两者完全一样。这也与设计稿 `:159` 早先「同屏峰值几何不是 GPU 瓶颈」的判断一致。
3. **显存 3~6 MB**，即便 4.5 倍也是从一个可忽略的基数涨起来的。

### 唯一真实的代价：首次加载

冷缓存（服务端发 `no-store`）下从设定视角到 45 张瓦片全部就位，best-of-3：

| 地形 | auto | grid | 倍数 | 字节倍数 |
|---|---|---|---|---|
| huabei（平缓） | 1093 ms | 1905 ms | **1.74×** | 2.49× |
| loess（崎岖） | 1969 ms | 2681 ms | 1.36×（三次 2681/2936/4501，噪声大） | 1.00× |

**这是纯字节代价，不是几何代价**，且只在平缓地形上出现。测量走的是 localhost，真实网络上会随带宽等比放大。在意这一项的用户选「速度」档即可 —— 它 24.6 MB，比现状的 44.5 MB 还小，加载只会比今天更快。

### 一条范围界定：全球底图不在本方案内，且应当继续用 `auto`

随包底图（`assets/terrain/base_z8/`）不经过 `build_terrain`，它是预先切好、随包分发、由 `graft_base_into` 物理植入任务目录的（`base_terrain.py:403`），构建脚本是 `scripts/build_global_base_terrain.ps1` 走 CLI 默认值。**三档预设只影响用户任务，不改变底图。**

而底图**应该继续用 `auto`**：它覆盖海洋与大片平原 —— 正是 martini 减面收益最大、grid 字节代价最高的地方 —— 而它的构建是一次性的，CPU 代价无所谓。这与「用户任务用 grid」不矛盾：两者的取舍条件本来就相反（一次性构建 + 全球平缓 vs 反复构建 + 用户指定 AOI）。

## 十、明确不要动的旋钮

**`tile_size` 保持 65。** 三个理由，按硬度排序：

1. 随包 base 是 65×65 且**物理植入**任务目录（`dem_task_tiler.py:167` `graft_base_into`），任务改 `tile_size` 会让 z7→z8 交界处顶点密度跳变（`global-base-build.md:147` 有原文记载）。
2. 实测也不划算：同分辨率下 `tile_size=129`（z13）对比 `tile_size=65`（z14），精度**完全相同**（RMS 均为 0.082），体积只小 9%，而扫描阶段测到它明显更慢（19.5 s vs 6.5 s，同一批扫描内的相对值）。
3. `tests/test_dem_task_tiler.py:56`、`tests/test_build_scripts_contract.py:48-62` 都钉着它。

**`max_error_k` 不必暴露。** 三档都用 `grid`，这个参数不参与计算。而且实测它本身就是个坏旋钮：K 从 0.30 加到 0.60，体积只再省 1.8%，RMS 却从 1.710 掉到 1.961（netherlands）；loess 上更是从 2.056 掉到 3.906。

**`workers` 可以另行放宽，但不属于本次三档。** 它是唯一零精度代价的速度旋钮，当前硬封顶 `min(4, cpu_count)`（`cesiumlab_terrain.py:1437-1442`）。20 核实测：

| 后端 | w=1 | w=4 | w=12 | w=20 | 每 worker 峰值 RSS |
|---|---|---|---|---|---|
| `auto` | 222.8 s | 66.3 s | **27.9 s** | 28.8 s | 255 MB |
| `grid` | 37.0 s | 11.4 s | 12.6 s | 8.9 s | 253 MB |

`auto` 路径放宽到 12 能再拿 2.4 倍，但 **`grid` 几乎不吃 workers**（w4→w20 只有 1.3 倍）—— 换后端已经把这块收益吃掉了。封顶 4 的原始理由（每 worker 一份 GDAL dataset）实测成立：253 MB/worker，12 个就是 3 GB。

## 十一、口径、可复现性与边界

### 三轴定义

- **精度** = 落盘 `.terrain` 解码后的三角网曲面，在固定地理采样点上对源栅格的 RMS（米）。两把尺子：甲 = 源栅格原生分辨率双线性**连续曲面**；乙 = 源栅格**像素中心的离散实测值**。正文除特别标注外用尺子甲。
- **速度** = `build_terrain` 整条金字塔（z0..max_level）的墙钟秒。
- **体积** = 落盘 `.terrain`（gzip 后）总字节。

### 采样点

每个 DEM 取 32 个 z14 瓦片、各内缩 6% 取 25×25 点 = 20000 点，`seed=7` 固定。锚在 z14 是为了让同一批地理点在任何 `max_level` 下都可比；`max_level > 14` 时按点分桶到各自所属瓦片（一个 z14 patch 会跨 4 张 z15 瓦片，按角点取单张会让越界点走外推）。

### 解码器自检（评测的地基，先验后用）

顶点数 / 三角形数与编码端逐一相等、三角形面积和 = 1.000000（完整覆盖单位方格）、martini 分支三角形与编码端输入逐条相同、插值无 NaN。

踩过一个坑：`encoded_indices` 在 uint16 上**回绕**（`cesiumlab_terrain.py:981` 明确写了这一点），解码必须按索引位宽取模，否则解出负索引。

### 四个测量陷阱（都实际踩到了，记下来免得重犯）

1. **磁盘写压力的顺序效应。** 每档连跑 3 次、每次写几百 MB 再删，脏页回写会拖进下一档的计时窗口 —— 同一配置（huabei `grid`@est）在「连跑」协议下测得 10.6 s，在「轮转 + `os.sync()` + 静置」协议下是 3.90 s，**差 2.8 倍**，而两者各自内部三次都很稳（10.6/10.9/11.2 vs 3.9/4.2/4.4）。**内部一致 ≠ 无系统偏差。** 第二节和第四节的时间全部是修正协议下的重测，两次独立重测在 `grid`@est 上互相吻合到 2% 以内（3.82/3.86/3.88 与 3.90/3.87/3.84）。
2. **RMS 的统计精度。** 32 个 patch 时 RMS 的 95% 自助区间为 **±5.8%**（400 次重采样）。所以**绝对值只有两位有效数字**。但同一 DEM 内所有配置共用同一批采样点，配对比较（比值）的精度远高于此。体积与瓦片数是确定性量，无噪声。
3. **隐藏标签页里 rAF 被节流，Cesium 的渲染循环根本不跑。** 用 `useDefaultRenderLoop: false` 自己泵 `scene.render()`。顺带这样测到的是**每帧真实开销**，不被 vsync 钳住 —— 对比几何负载正需要这个。
4. **隐藏标签页里 `setTimeout` 被钳到约 1 秒一次。** 渲染泵里的 `await sleep(4)` 实测变成 1917 ms、整个循环只跑了 1 帧，瓦片永远等不到加载完。改用 `MessageChannel` 让出事件循环（不受定时器节流影响）后，同样的 1200 ms 窗口跑满 56 帧。

### 本次没有测的（不要把结论外推过去）

- 多文件 VRT 输入（只测了单 tif）；
- 大面积 nodata 的 DEM；
- 非 Copernicus 源（不同的高程量化与噪声特性会影响 gzip 率）；
- **客户端的观感**。第八节测的是帧时、同屏几何量与加载耗时，**没有**做视觉对比（着色、地平线轮廓、坡面锯齿在人眼下的差异）。本文的「精度」始终是几何保真度。
- 真实网络条件下的加载（第八节走的是 localhost，无带宽与 RTT 约束）。
