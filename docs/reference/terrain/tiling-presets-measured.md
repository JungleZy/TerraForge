# 高程切片三档预设：实测选型

> **测量时间**：2026-08-08 | 6 个真实 Copernicus GLO-30 granule（1°×1°，坡度中位 0.51~38.85 覆盖极平原到黄土塬）、102 组完整金字塔构建、精度全部从**落盘瓦片解码后**对源栅格量得。
> 本文只做测量与选型，**没有改动任何生产代码**。测量台在 `~/.cache/mapdl-probe/preset_eval/`。

---

## 一、结论先行

**三档定义**（`tile_size` 恒为 65 不动，`max_error_k` 在 grid 后端下不起作用）：

| 档位 | `triangulator` | `max_level` | `normals` | 顶点间距 |
|---|---|---|---|---|
| **精度** | `grid` | `est + 1` | 跟随光照开关 | ≈ 0.3× 源像素 |
| **均衡**（默认） | `grid` | `est` | **关** | ≈ 0.6× 源像素 |
| **速度** | `grid` | `est − 1` | **关** | ≈ 1.2× 源像素 |

`est` = `GeographicTilingScheme(tile_size=65).estimate_max_level(源像素度数)`，**按源 DEM 分辨率现算**，不是固定值。

**三个都用 `grid`，一个都不用现行的 `auto`。** 这不是折中，是实测：现行默认 `auto` 在 6 个 DEM 上**一个 Pareto 前沿都没进**，被三轴全面支配。

**质量档位靠 `max_level` 拉开，不靠简化后端。** 两者都能换体积，但兑换率差 2.4~3.9 倍（见第四节），且层级旋钮**省时间**、后端旋钮**多花 2.4~4.0 倍时间**。

## 三、为什么现行默认必须换掉

### 3.1 它不在 Pareto 前沿上 —— 6 个 DEM，0 次

对 14 个候选配置做三轴（墙钟 / 字节 / RMS，全部越小越好）严格支配判定：

| 配置 | 进入前沿次数 |
|---|---|
| `grid` + 法线关 @est | **6 / 6** |
| `grid` @est−1 | **6 / 6** |
| `auto` @est−1 | **6 / 6** |
| **`auto` K=0.15 @est（现行默认）** | **0 / 6** |
| `martini` K=0.15 @est | 0 / 6 |
| `auto` K=0.30 / K=0.60 / K=0.05 | 0 / 6 |
| `grid` @est（法线开） | 0 / 6 |

现行默认在每个 DEM 上都被具体配置三轴全面支配：5 个 DEM 上被 `grid @est−1` 支配，6 个 DEM 上被「同配置但关法线」支配。

### 3.2 简化后端在崎岖地形上是负收益

`martini` 的减面在字节上并不总是赚。gzip 后规则网格约 0.91 字节/三角形、Martini 约 4.04 字节/三角形（每个三角形贵 4.43 倍），**减面必须超过 77.4% 才在字节上打平**。崎岖地形减不到。

loess @est 实测（法线统一关，只比几何）：

| 后端 | 体积 | RMS |
|---|---|---|
| `grid` | 94.5 MB | 0.520 m |
| `martini` | **143.9 MB** | 1.082 m |

**martini 比 grid 大 52%，精度还差 2.1 倍。** `auto` 逐瓦片择优能识别出这一点（loess 上它 98.8% 的瓦片选了 grid，产物与纯 grid 几乎一致），但代价是**两个后端各编一遍各压一遍**——白花的 CPU。

### 3.3 时间花在哪：`rtin_extract` 占 58%

单瓦片成本分解（loess z14，`tile_size=65`，`auto` + 法线，进程内 best-of-N）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| `rtin_extract` 自适应三角化 | 4.43 ms | **57.7%** |
| 法线（采样 + 叉积） | 0.79 ms | 10.2% |
| gzip(martini) | 0.78 ms | 10.2% |
| encode(martini) | 0.66 ms | 8.6% |
| encode(grid) | 0.38 ms | 4.9% |
| gzip(grid) | 0.35 ms | 4.5% |
| **DEM 采样** | **0.19 ms** | **2.5%** |
| `rtin_errors` | 0.10 ms | 1.3% |

两个反直觉点：

- **GDAL 采样只占 2.5%**，不是瓶颈。切片是 CPU-bound 在纯 Python 的三角化上。
- `rtin_extract`（`rtin.py:106-159`）是纯 Python 递归，每个三角形 3 次 dict 查找，成本正比于**产出三角形数** —— 所以它在崎岖地形上更贵（loess 2606 三角形 → 4.43 ms）、平缓地形上便宜（huabei 930 三角形 → 1.02 ms）。这就是 `auto` 相对 `grid` 的减速是 1.9×~4.5× 随地形浮动的原因。

改用 `grid` 直接绕开整条 rtin 路径 + 第二次编码 + 第二次压缩：**7.68 ms → 1.71 ms，单瓦片快 4.5 倍**。

## 四、为什么档位靠 `max_level` 而不是靠简化后端

两个旋钮都能拿精度换体积。从「`grid` @est、法线关」这个共同基线出发，各自走一步：

**性价比 = 体积压缩倍数 ÷ RMS 劣化倍数**，>1 表示这笔交易划算。

| 地形 | 旋钮 | 尺子甲<br>（连续双线性曲面） | 尺子乙<br>（源像素中心实测值） | 时间 |
|---|---|---|---|---|
| huabei | 降一级 | 3.85× ÷ 2.63× = **1.46** | 3.85× ÷ 1.85× = **2.09** | **省 2.7×** |
| | 换 `auto` | 2.49× ÷ 6.77× = **0.37** | 2.49× ÷ 3.33× = **0.75** | 多花 3.8× |
| jiangnan | 降一级 | 3.82× ÷ 2.69× = **1.42** | 3.82× ÷ 1.90× = **2.00** | **省 3.4×** |
| | 换 `auto` | 1.51× ÷ 2.77× = **0.55** | 1.51× ÷ 1.79× = **0.85** | 多花 5.6× |
| loess | 降一级 | 3.79× ÷ 2.84× = **1.34** | 3.79× ÷ 1.94× = **1.95** | **省 3.4×** |
| | 换 `auto` | 1.00× ÷ 1.00× = 1.00 | 1.00× ÷ 1.00× = 1.00 | 多花 4.3× |

（loess 那两行是 1.00：法线关掉后 `auto` 98.8% 选 grid，两者本就是同一个产物。）

两把尺子给出同一个方向：**层级旋钮的效率是简化后端的 2.4~3.9 倍，而且它省时间、后端花时间。**

### 层级的兑换率高度稳定，与源分辨率无关

把 loess 重采样成 3″（93 m）和 9″（278 m），各自建 5 个层级：

| 源分辨率 | 每加一级的体积倍数 | 每加一级的精度倍数 |
|---|---|---|
| 1″ (31 m) | ×3.8 / ×3.6 / ×3.05 | ÷2.84 / ÷2.74 / ÷2.91 |
| 3″ (93 m) | ×3.6 / ×3.1 | ÷2.77 / ÷2.80 |
| 9″ (278 m) | ×2.7 / ×2.8 | ÷3.05 / ÷2.92 |

**加一级 ≈ 3.3 倍体积换 2.8 倍精度**，六组数据全部落在这个区间。这就是三档能等距拉开、且行为可预测的依据。

### `est` 是约定，不是精度悬崖 —— 我原来的两个假设都错了

我先后假设过「超出源分辨率的层级是纯浪费」，用两把尺子各验一次，**两次都被数据否掉**：

| loess | 尺子甲（连续双线性曲面） | 尺子乙（源像素中心实测值） |
|---|---|---|
| z13 | 1.5146 m | 2.4467 m |
| z14（= est） | 0.5342 m | 1.2602 m |
| z15 | 0.1947 m | **0.6331 m** |

越过 `est` 之后**两把尺子都在继续降**，没有平台期。原因：`est` 层顶点间距（19.1 m）虽已细于源像素（31 m），但顶点不落在像素中心上，取值是「双线性采样 → 再线性插值」的二次残差，只随网格加密平滑收敛，不存在阈值。

**所以 `estimate_max_level` 是一个约定（间距 ≈ 源像素），不是物理门槛。** 拿它当「均衡」的锚点是因为它可解释、可按源自适应，不是因为越过它就没用了。

## 五、法线：应该从档位里拆出来，单独一个开关，默认关

法线（`octvertexnormals`）**对几何精度零贡献** —— 开关两侧 RMS / P95 / 最大误差逐位相同。它的代价：

| DEM | 关 | 开 | 字节代价 | 时间代价 |
|---|---|---|---|---|
| huabei | 94.6 MB / 10.6 s | 127.2 MB / 23.2 s | **+35%** | **2.19×** |
| jiangnan | 91.9 MB / 6.2 s | 153.3 MB / 12.8 s | **+67%** | **2.07×** |
| loess | 94.5 MB / 8.1 s | 189.3 MB / 12.3 s | **+100%** | **1.52×** |

而前端 `enableLighting` **默认是关的**（`static/js/terrain_lighting.js:46-52`），偏好只存 localStorage 键 `tf-terrain-lighting`（`:34`、`:72`），不进配置表。

### 还有一条非显然的连锁反应：法线会把 `auto` 推向更差的后端

法线是每顶点 2 字节，`grid` 顶点最多（4225）、被罚得最狠，于是逐瓦片择优被系统性地推向 martini：

| loess | 选 martini | 选 grid | martini 占比 | RMS |
|---|---|---|---|---|
| `auto` 法线**开** | 8098 | 3973 | **67.1%** | 1.040 m |
| `auto` 法线**关** | 146 | 11925 | **1.2%** | **0.520 m** |

**关掉法线不只省时间省体积，还顺带让择优选对后端，精度直接翻倍。** 这条在换成 `grid` 之后自动消失（不再有择优），但它解释了现行默认为什么精度那么差。

### 风险：关法线是**静默**降级

`normals=False` 会让 `layer.json` 的 `extensions` 写成 `[]`（`cesiumlab_terrain.py:1548`）。Cesium 的 `hasVertexNormals` 是 **provider 级单一标志**，于是：

- 光照按钮点了没有地形明暗，退化成全球日夜渐变，**全程零报错**；
- 植入的随包 base 自带法线也一起作废（`merge_base_availability` 不修改 `extensions`，`layer_json.py:137-142`）。

**这个项目栽过三次「作业 completed、HTTP 200、前端不报错、就是不对」的跟头。** 所以建议法线做成独立勾选项并在 UI 上写明「关闭后地形光照不可用」，而不是藏在档位里静默生效。切完再想开只能重切——法线是烘焙进瓦片的。

## 六、顺带查出的现存缺陷：`maxzoom` 不看源分辨率

应用侧**恒传** `maxzoom`（配置键 `terrain_local_maxzoom` 默认 14，`database.py:91`；`dem_task_manager.py:307-314`），`build_terrain` 里的 `estimate_max_level` 因此从不生效。后果双向：

- **源比 30 m 粗时超建**。3″（93 m）DEM 建到 z14 = 77.4 MB / 12071 张；按 `est`(=12) 建 = 6.9 MB / 1445 张。**11 倍体积**换来的是对同一批 93 m 数据更平滑的插值，不含任何新地形。
- **源比 30 m 细时欠建**。5 m DEM 的 `est` 约 17，被固定的 14 截断，源数据的细节根本没进瓦片。

三档按 `est` 现算，等于顺手修掉这条。对最常见的 1″ Copernicus GLO-30，`est` 正好 = 14，**层级与今天一致**，不会让现有用户的产物层级发生意外变化。

## 九、明确不要动的旋钮

**`tile_size` 保持 65。** 三个理由，按硬度排序：

1. 随包 base 是 65×65 且**物理植入**任务目录（`dem_task_tiler.py:167` `graft_base_into`），任务改 `tile_size` 会让 z7→z8 交界处顶点密度跳变（`global-base-build.md:147` 有原文记载）。
2. 实测它也不划算：同分辨率下 `tile_size=129`（z13）对比 `tile_size=65`（z14），精度完全相同（RMS 0.082），但**慢 3 倍**（19.5 s vs 6.5 s），体积只小 9%。
3. `tests/test_dem_task_tiler.py:56`、`tests/test_build_scripts_contract.py:48-62` 都钉着它。

**`max_error_k` 不必暴露。** 三档都用 `grid` 后端，这个参数不参与计算。而且实测它本身就是个坏旋钮：K 从 0.30 加到 0.60，体积只再省 1.8%，RMS 却从 1.710 掉到 1.961（netherlands）；loess 上更是从 2.056 掉到 3.906。

**`workers` 可以另行放宽，但不属于本次三档。** 它是唯一零精度代价的速度旋钮，当前硬封顶 `min(4, cpu_count)`（`cesiumlab_terrain.py:1437-1442`）。20 核实测：

| 后端 | w=1 | w=4 | w=12 | w=20 | 每 worker 峰值 RSS |
|---|---|---|---|---|---|
| `auto` | 222.8 s | 66.3 s | **27.9 s** | 28.8 s | 255 MB |
| `grid` | 37.0 s | 11.4 s | 12.6 s | 8.9 s | 253 MB |

`auto` 路径放宽到 12 能再拿 2.4 倍，但 **`grid` 几乎不吃 workers**（w4→w20 只有 1.3 倍）—— 换后端已经把这块收益吃掉了（同为 w4，grid 11.4 s vs auto 66.3 s = **5.8 倍**）。封顶 4 的原始理由（每 worker 一份 GDAL dataset）实测成立：253 MB/worker，12 个就是 3 GB。

## 十、口径、可复现性与边界

**三轴定义**

- **精度** = 落盘 `.terrain` 解码后的三角网曲面，在固定地理采样点上对源栅格的 RMS（米）。两把尺子：甲 = 源栅格原生分辨率双线性连续曲面；乙 = 源栅格像素中心的离散实测值。正文除特别标注外用尺子甲。
- **速度** = `build_terrain` 整条金字塔（z0..max_level）的墙钟秒。
- **体积** = 落盘 `.terrain`（gzip 后）总字节。

**采样点**：每个 DEM 取 32 个 z14 瓦片、各内缩 6% 取 25×25 点 = 20000 点，`seed=7` 固定。锚在 z14 是为了让同一批地理点在任何 `max_level` 下都可比；`max_level > 14` 时按点分桶到各自所属瓦片（一个 z14 patch 会跨 4 张 z15 瓦片，按角点取单张会让越界点走外推）。

**解码器自检**（评测的地基，先验后用）：顶点数/三角形数与编码端逐一相等、三角形面积和 = 1.000000（完整覆盖单位方格）、martini 分支三角形与编码端输入逐条相同、插值无 NaN。踩过一个坑：`encoded_indices` 在 uint16 上**回绕**（`cesiumlab_terrain.py:981` 明确说明），解码必须按索引位宽取模，否则解出负索引。

**统计稳定性**：32 个 patch 时 RMS 的 95% 自助区间为 **±5.8%**（400 次重采样）。所以**绝对值只有两位有效数字**。但同一 DEM 内所有配置共用同一批采样点，配对比较（比值）的精度远高于此。体积与瓦片数是确定性量，无噪声。

**墙钟噪声**：小任务（< 4000 张）的墙钟被进程启动 + GDAL 打开主导，扫描阶段观察到过方向相反的异常值。**第二节的表全部是 workers=4、best-of-3 的独立复测**，扫描阶段的时间数只用于定性。

**本次没有测的**（不要把结论外推过去）：

- 多文件 VRT 输入（只测了单 tif）；
- 大面积 nodata 的 DEM；
- 非 Copernicus 源（不同的高程量化与噪声特性会影响 gzip 率）；
- **客户端实际渲染**——帧率、显存、解析 CPU 全部未测。本文的「精度」是几何保真度，不是观感。
